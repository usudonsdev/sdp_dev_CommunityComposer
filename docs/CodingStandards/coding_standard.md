# コーディング規約

本プロジェクトでは、Pythonコードの可読性、保守性、チーム内での統一性を高めるため、
[Google Python Style Guide](https://google.github.io/styleguide/pyguide.html) を基本規約として採用する。

## 適用範囲

- Pythonで実装するすべてのソースコード
- Pythonのテストコード
- Pythonコードを生成・修正する場合のLLM支援コーディング

## 基本方針

- 原則として Google Python Style Guide に従う。
- 判断に迷う場合は、既存コードの書き方を優先する。
- 規約に従うことで可読性が下がる場合は、チームで相談して例外を認める。
- 例外的な実装を行う場合は、理由が分かるようにコメントを残す。

## 主な規約

### 命名規則

- モジュール名・パッケージ名は `lower_snake_case` とする。
- 関数名・メソッド名・変数名は `lower_snake_case` とする。
- クラス名は `PascalCase` とする。
- 定数名は `UPPER_SNAKE_CASE` とする。
- 非公開の変数・関数・メソッドは先頭に `_` を付ける。

### インポート

- インポートはファイルの先頭にまとめて記述する。
- 標準ライブラリ、外部ライブラリ、プロジェクト内モジュールの順に並べる。
- ワイルドカードインポートは使用しない。
- 相対インポートよりも、パッケージ名を含む明確なインポートを優先する。

### 書式

- インデントは半角スペース4つとする。
- 1行の長さは原則80文字以内を目安とする。
- 不要な空行、未使用の変数、未使用のインポートは残さない。
- 複数文を1行にまとめる書き方は避ける。

### コメント・Docstring

- モジュール、クラス、関数には必要に応じてDocstringを記述する。
- コメントは処理内容そのものではなく、理由や背景を説明するために使う。
- 複雑な条件分岐、外部API通信、認証処理、例外処理には補足コメントを付ける。

### 型ヒント

- 関数の引数と戻り値には、できるだけ型ヒントを付ける。
- 型ヒントにより可読性が下がる場合は、無理に複雑な型を書かない。
- `Any` の使用は必要最小限にする。

### 例外処理

- 補足する例外はできるだけ具体的な例外型にする。
- 理由のない `except:` や `except Exception:` は使用しない。
- 例外を握りつぶさず、必要に応じてログ出力やエラーメッセージ表示を行う。

### Flaskに関する規約

- ルーティング処理は `routes/` または `blueprints/` に配置する。
- DBモデルは `models/` に配置する。
- フォームやリクエスト値の検証処理は `validators/` または `forms/` に分離する。
- ビジネスロジックは `services/` に分離する。
- テンプレートファイルは `templates/`、静的ファイルは `static/` に配置する。
- ルート関数には複雑な処理を書かず、サービス層の関数を呼び出す。
- APIとしてJSONを返す場合は、レスポンス形式を統一する。

### セキュリティ

- パスワード、APIキー、トークンなどの秘密情報をソースコードに直接書かない。
- 個人情報や認証情報をログに出力しない。
- ユーザー入力値は必ずバリデーションする。
